Skillforge · v2.3.0 · 14 skills, zero runtime

Skillforge Field Manual

Fourteen markdown skills and one always-on agreement. The skills supply judgment; the artifacts under context/ are what survives the session. Nothing here assumes anything else here is installed.

9 work skills 5 dev skills 8 shape templates 11 artifact types 1 always-on file
Section 01

The skills

Each row: what it does, what it leaves behind, and where work usually goes next. next → is the common path, not a requirement — routing is a choice the model makes, and none of these call each other.

skills/work — any kind of work
grilling
Interrogates you round by round until a plan or decision has no unstated assumptions. Facts are its job; decisions stay yours.
leaves nothing — no filenext → shape
shape
Turns a raw request into one written artifact — brief, roadmap, decision record, PRD, vision, stack register, test strategy, or opportunity map. Resolves the open decisions first, then writes.
leaves one artifactnext → phasing / executing
phasing
Writes and then works a phased plan — per-phase verification and a durable checklist that survives a new session or a compaction. Also the resume path.
leaves plan.mdnext → executing / tdd
executing
Steers a shaped change to done without drifting from it: readiness check, an ordered ladder for resolving ambiguity from the written record, and closing the loop. Optional — shape is the backbone.
leaves evidence, updated artifactsnext → review
delegating
Decides what to hand a subagent and how to brief it — bounded task, own paths, report contract, and the cheapest model that can do it.
leaves a verified resultnext → back to caller
handoff
A compact continuation note so a fresh agent can pick the work up safely. Written for an agent, not a person. Goes to temp, not the repo.
leaves a temp notenext → new session
digest
One self-contained HTML page a person can read, keep and forward — recap, explainer, decision write-up, status report.
leaves a pagenext → send it
retro
Looks back at finished work and proposes changes to the setup, not the work — where your attention went unnecessarily, which corrections repeated, what should become a rule, a check or a script.
leaves ranked proposalsnext → writing-skills
writing-skills
Authors, edits or retires a skill — including noticing from the session that one is needed. New artifact types are templates here, never new skills.
leaves a skill, or removes onenext → done
skills/dev — only on a codebase
orienting
Gets up to speed in an unfamiliar repo and proves the commands by running them. Finds the conventions in force, the hot paths, and what nobody tests. Stops before planning a change.
leaves understandingnext → shape / phasing
debugging
Builds the reproduction loop first, then one falsifiable hypothesis at a time, with a three-strikes stop. No fix before the cause is named.
leaves a repro = the regression testnext → tdd / review
tdd
One behavior at a time: write the failing test, watch it fail for the right reason, then make it pass. Refactoring is left to review.
leaves tests + the behaviornext → review
spike
Answers “can this even work” with the smallest throwaway that settles it — then keeps the answer and deletes the code. Not for a bug, and not for known-feasible work.
leaves an answer, no codenext → shape
review
A gate: findings first, severity-ordered, each with a location and a fix. Judges an implementation against its spec, or someone else's review against the code.
leaves findings, or a clean verdictnext → executing / handoff

The one rule that shapes all of this

No skill assumes another is installed. Copy two of the fourteen into a locked-down repo and they still work. That is why the grilling loop is restated inside shape, and why every cross-reference reads “if one is installed” rather than naming a dependency.

Section 03

What the artifacts are

The skills are how; these are what survives. foundation/ is standing context, rarely written and often read. changes/<id>/ is one unit of work, where <id> is NN-slug — the same id the roadmap row carries.

context/foundation/ — standing

vision.md
Direction, and a ranked priority order so conflicts between two good things have an answer. Cannot authorise new scope.
shape · owner-written
roadmap.md
Change index. Ids are the change-ids; a status column closes the loop.
shape
tech-stack.md
What was chosen and which hard barrier forced it. Chosen by elimination, not preference.
shape
test-strategy.md
Ranked risks, which level holds each, and what is deliberately untested.
shape
decisions/<nnn>-<slug>.md
One contested, hard-to-reverse choice each, with a one-line Standing rule so the set is greppable.
shape
opportunities/<slug>.md
Build / buy / thin complement / wait — before a brief exists.
shape
prd-<slug>.md
Product intent, when that and not the technical approach is what is unclear.
shape

context/changes/<id>/ — one change

brief.md
Problem, goal, non-goals, constraints, risks, and the verification that proves it worked. Non-goals and verification are mandatory.
shape
plan.md
Phases, each with its own runnable verification, plus the progress checklist that is the durable state.
phasing
questions.md
Parked blocking questions under stable ids (q1, q2), each with status and what it holds up.
executing
calls.md
Provisional decisions made when no owner was reachable — the question, the answer taken, the rung it came from, what would overturn it.
executing
[ ] not started — nothing touched
[~] state unknown — run its Verify to find out
[x] verified — its Verify passed, in a session

The middle marker is the point: it is what a compaction boundary actually produces. A resumed run settles [~] by running that phase's verification — never by assuming it finished, and never by redoing it blind.

Section 04

The ideal full process

Seven steps, in order, because here the order is the information. Each has a gate — the observable thing that has to exist before the next step is worth starting. Most real work skips steps; skipping a step is a decision to state, skipping its gate is not.

1
Decide it is worth doingopportunity map
Classify the friction against its real frequency and cost, then choose build, buy, a thin complement, or wait. Most “we should build a tool for this” ideas lose to the default that already exists.
gate a verdict, and the smallest next step that tests it
2
Write the direction down oncevision · tech-stack
The standing artifacts that later answer questions nobody thought to ask. Vision's ranked priority order is what makes it usable at a fork rather than decorative.
gate two goods in tension have a stated winner
3
Divide the workroadmap
An index, not a plan: each entry small enough to brief and build on its own, in dependency order, with the pre-mortem and devil's-advocate answers written down honestly. Entries reserve their change-ids here.
gate every entry has an observable “done when”
4
Shape one changegrilling → shape
Interrogate until nothing is silently assumed, confirm the settled decisions with the owner, then write the brief. It records their decisions, not your inferences.
gate non-goals named, verification runnable
5
Sequence itphasing
Phases that each leave the codebase working, ordered so the phase that could invalidate the plan comes first. Named files per phase, exact commands, no placeholders.
gate every phase names its own verification
6
Build it without driftingexecuting + tdd / debugging
One phase at a time, marked [~] before it starts and [x] only once its verification passes with the output shown. Every changed line traces to something the brief asks for; discovered out-of-scope work gets written down, not done.
gate fresh output, this session, per phase
7
Judge, then close the loopreview → retro
Review against the brief rather than against taste. Then the record says what is now true: roadmap status updated, evidence attached, anything durable and surprising written as a decision record, and anything the work proved wrong amended in the brief.
gate every requirement traced, every non-goal still undone
Where it stops being ideal

A trivial, fully specified task — a typo, a rename, a one-line fix — needs none of this, and gating it is ceremony. The floor is protected by judgment, not by structure: both shape and executing say to skip themselves on work too small to deserve them, and nothing enforces that but the reading.

Section 05

The ambiguity ladder

What executing climbs when the artifact does not settle a fork. Stop at the first rung that answers, and say which one did. When two rungs answer differently the higher wins — and the disagreement gets named, because a real conflict between artifacts is a defect in them rather than a tie to break quietly.

1
The brief — goal, non-goals, verification.
2
The plan — a later phase has often already decided it.
3
The roadmap — does a neighbouring change already own this?
4
The standing registers — the stack for conventions in force, the test strategy for what is worth proving.
5
The vision — its priority order breaks ties between competing goods. It never authorises new scope.
6
The decision records — has this argument already been had and settled?
7
The blocker register — has it already been asked, and has an answer come back since?
8
The owner — or, on a declared unattended run, decide only where the answer is grounded (name the rung, quote the line) and bounded (being wrong costs no more than redoing this change). Otherwise park it and carry on with what it does not block.
Blocking is an outcome

A fork the whole ladder cannot settle usually means a requirement is wrong or missing, and knowing that beats a confident guess. Attended: ask. Unattended: park it, log it, and finish everything it does not hold up.

Unattended is declared, never inferred

Only the invocation or an Execution mode: unattended line in the always-on file turns it on. Everything else is attended, ambiguity included — failing to find a way to ask is not permission to decide.

Section 06

What is deliberately absent

  • No router or gateway skill. Hosts already inject every skill's name and description; the always-on file carries the routing rule in two lines.
  • No estimates. phasing refuses them unless asked. Sequence and verification are the value.
  • No orchestration between skills. tdd, debugging and review are independent tools; executing names the gate each step must pass and defers to whatever is installed.
  • No new skill for a new document type. Artifacts are templates under shape/references/, so a new type never becomes a new routing competitor.
  • No invariant as a skill. Anything that must hold on every response lives in the always-on file, because routing is a choice the model makes.
  • No runtime in the core. Pure markdown. The one script is optional and nothing depends on it.
Known open gaps, as of v2.3.0

questions.md has no attended writer yet — shaping is meant to mint the register at brief time so q ids exist from the start. calls.md has no rung, so a second unattended run can re-decide a settled fork. The roadmap's ready and dropped states have no writer. All three are recorded in docs/DESIGN.md rather than quietly outstanding.
